# 최규원 3페이즈 — 기억 전장·카메라·프레임 안정화

## 요구사항과 현재 구현

- 3페이즈에서는 기존 플레이어 중심 전투 카메라를 유지하면서 다섯 기억마다 조금 더 위에서 내려다보도록 한다.
- 배서준 해일은 카메라를 수평선 먼 곳으로 강제 이동시키지 않는다. 백색 성당의 높은 벽·지붕은 해일 접근 중에만 디더링 기반 반투명으로 보이고 전투 바닥은 항상 불투명하다.
- 기억 공격의 방향과 경고는 인게임 텍스트·범위표 대신 보스 동작과 입체 물체 자체로 전달한다. 광역기 판정·회피 루트는 변경하지 않는다.

## 느려지는 구간의 코드상 원인

정량적인 **수정 전 FPS·GPU 타임은 아직 미측정**이다. 다음은 기존 코드에서 직접 확인한 구조적인 비용이며, 실제 사용자의 기기에서 심한 렉의 기여율이 확정되었다는 뜻은 아니다.

1. `gyuwon-recall-maps.mjs`: 전장 객체는 처음부터 4개 만들어져 있었으나, 처음 보일 때 GPU가 재질·텍스처·정점 버퍼를 준비해야 했다. 특히 원본 카메라 가림 구현은 렌더마다 메모리 전장 전체를 순회하며 각 객체의 재질을 복제본으로 교체/복원했고, 별도 셰이더 변형을 만들었다.
2. `gyuwon-spectacle.mjs`: 기억 해일이 시작될 때마다 120×35 수면 격자, 앞뒤 면, 통로 경계 연결, 법선 계산, 새 `MeshPhysicalMaterial` 생성 작업이 발생했다.
3. 해일 카메라가 전투 중 갑자기 x축으로 약 150m 이상 이동하고 FOV를 바꿔 시야와 가시성 검사 대상이 급변했다.

## 적용

- `createGyuwonRecallMaps.prewarm`은 전투 시작 로딩 게이트 안에서 네 원본 전장을 하나씩 숨겨진 16×16 렌더타깃에 컴파일·그리며 정점 버퍼·텍스처 업로드를 앞당긴다. 실제 기억 전환은 루트의 `visible` 토글만 사용한다.
- 매 프레임마다 전체 메모리 전장을 검사하던 `createCameraVisibility`의 재질 스와핑을 제거했다. 해일 때 필요한 성당의 투과성은 **처음 생성한 일부 구조물의 안정적인 alpha-hashed 재질**로 표현한다.
- `createGyuwonMemoryWave`는 해일 정점·연결면·법선을 한 번 계산하여 살아 있는 동일한 3D 메시를 다음 기억 공격에 재활용한다. `gap` 이동으로 통로를 실제 판정과 같은 위치에 둔다. 해일 최상단/통로 가장자리의 물거품과 정점 셰이더 물결은 게임 피해 판정과 분리되어 있다.
- `createGyuwonSpectacle.prewarm`도 5가지 기억의 셰이더와 메시를 첫 공격 전에 숨겨진 렌더타깃에 등록한다. 대형 검은 bevel이 있는 메시, 광대의 기억은 주름진 천 무대, 도박 기억의 룰렛은 인스턴싱으로 정돈했다.
- 모든 GPU 추가 리소스는 보스전을 닫을 때 `dispose`한다.

## 성능 검사 기준

- 새 테스트: `tests/gyuwon-memory-performance.test.mjs`. 5개 기억 카메라, 카메라 강제 이동 제거, 해일 메시 1회 생성, 통로 위치, 자원 해제.
- 기존 테스트 확장: `tests/gyuwon-recall.test.mjs`. 맵 4개 1회 생성, 초기 컴파일 4회, 반복 전환에서 빌드 수 일정, 해일 중 성당 가림 감소, 바닥 불투명 유지.
- 실기기/브라우저에서 수정 전·후 비교할 항목: **전장 전환 순간의 상위 1% 프레임 시간**, 첫 해일 발동 프레임, 렌더 드로콜 및 삼각형 수, 텍스처 메모리, PC/모바일에서의 전조 가독성.
- **미검증 항목**: 실제 기기에서 최소 FPS, 평균 FPS, 모바일 메모리 사용량, 수평선 해일 육안 가독성. 코드 구조만으로 성능 문제 완전 해결을 보증하지 않는다.
