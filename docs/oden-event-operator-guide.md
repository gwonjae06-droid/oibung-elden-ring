# 오든링 엔딩 이벤트 — 관리자 설치 및 상품 지급 안내

> **현재 상태: 전용 프로젝트 설치 완료, 이벤트 공개 잠금 유지.**
> 2026-11-10 새 Supabase 프로젝트 `odenring` (`pmkhffwuzwxokqupuxkn`)에
> 이벤트 테이블과 `oden-event` Edge Function (`index.js`, `risk.js`)을 설치했다.
> 게임 설정의 프로젝트 주소와 공개 키도 새 프로젝트로 교체했다.
> 실제 게임의 전체 플레이 및 PC·모바일 입력 검증은 아직 완료하지 않았다.
> 검증이 끝날 때까지 `src/oden-event-config.mjs`의 `enabled:false`를 유지한다.

## 1. 이벤트 공개 전 확인
1. [Supabase Dashboard](https://supabase.com/dashboard/project/pmkhffwuzwxokqupuxkn)에서
   전용 프로젝트를 확인한다. 이전 프로젝트의 데이터나 연결 설정은 변경하지 않았다.
2. DB의 이벤트 테이블에는 RLS가 활성화되어 있고, anon/authenticated 직접 접근은 차단되어 있다.
   공개 RLS 정책이 없는 것은 서버 함수만 기록을 관리하도록 한 의도된 설정이다.
3. 인증 함수는 자체 `X-Oden-Token` 참가자 인증을 사용한다(`verify_jwt=false`).
   서비스 키는 서버에만 두고 브라우저나 저장소에 공개하지 않는다.
4. 참가 등록 → 이권재 → 오슬우 → 박성원 → 배서준 → 최규원 800HP 이후
   3D 엔딩(164초) → 클레임 코드 표시까지 실제 게임에서 테스트한다.
   PC·모바일의 정상 입력, 의심 입력 관찰과 소명 UI도 확인한다.
5. **모든 검증 통과 후에만** `src/oden-event-config.mjs`의 `enabled:true`를 배포한다.
   그 전에는 이벤트 UI가 나타나지 않는다.

## 2. 친구가 하는 일
- 메인화면의 **엔딩 이벤트**를 열고 닉네임을 등록한다.
- 이벤트 저장은 `oibung.event.<eventId>.<participantId>.*`에 저장한다.
  **주의:** 이벤트 공개 전에 안내해야 한다. 이벤트 활성화 이후 첫 접속 시
  기존 일반 게임의 클리어·대장간·단체사진 기록은 한 번 초기화된다.
  그 후 이벤트 전용 저장소와 일반 진행 기록은 분리되어 유지된다.
- 이벤트 기록에서는 개발용 메인화면 4·5회 클릭, 대장간 개발자 입력,
  최규원 일시정지 4회 수 선택과 세미콜론 연도 스킵을 비활성화했다.
- 보스 클리어는 단계별로 서버에 보고된다. 최규원 전투의 마지막
  3D 후일담 시작 시 서버에서 시간을 기록하고, 완주 후 인증번호를 발급받는다.
- 바뀐 메인화면에 **닉네임 + ODEN-XXXXXXXXXXXX 코드**가 보이도록 캡처해
  등록 때 안내한 카카오톡/디스코드 계정으로 제출한다.

## 3. 네가 상품 지급을 심사하는 법
1. [Supabase Table Editor](https://supabase.com/dashboard/project/pmkhffwuzwxokqupuxkn/editor)에서
   `public.oden_event_participants` 테이블을 연다.
2. `claim_code` 열에서 친구가 보낸 번호를 정확하게 검색한다.
3. `nickname`, `event_id`, `stage=4`, `completed_at`이 있는지 확인한다.
   `paid_at`이 이미 존재한다면 **절대 중복 지급하지 않는다**.
4. 스크린샷의 코드와 닉네임이 일치하고, 실제 그 친구가 등록한 계정에서
   보낸 것인지 확인한다.
5. 의심스러우면 지급 전에 플레이 기록/라이브 시연을 요청한다.
   고정 입력 간격이나 피격 횟수만으로 자동 탈락시키지 않는다.
6. 정상 승인 시 **Table Editor에서 `review_status`를 `approved`** 로 바꾼다.
   상품을 실제로 보낸 **이후** `paid_at`에 현재 UTC 시각을 기록한다.
   거절 시에는 `rejected`를 선택한다.
7. 심사는 서버 관리자만 수행한다. 클라이언트가 승인·지급 상태를
   수정하는 API는 없다. 참가자 DB 테이블은 RLS + anon/authenticated 권한 차단으로 보호된다.

## 4. 주의: 부정행위 방지의 한계
- 서버가 **일련번호와 순서·진행 시각을 남긴다**는 것과
  **실제 게임을 정직하게 플레이했다는 것**은 다르다.
- 브라우저가 전투를 계산하므로, 잘 아는 사람은 변조된 JS에서
  정해진 순서로 이벤트 API를 호출하고 시간 조건을 기다릴 수 있다.
- 서버는 최규원 최종 후일담 시작 보고 후 **155초 이내** 인증을 거부한다.
  이는 즉석 가짜 완료를 줄일 뿐, 충분히 기다린 가짜 완료까지 막지는 못한다.
- AI 자동 플레이를 확실히 구분하지 못한다.
- **경품 가치가 크거나 의심스러운 신청만 라이브/영상 추가 검증**하는 것이
  이 소규모 이벤트 설계의 현실적인 정책이다.

## 5. 비상 운영 원칙
- 서버 접속 장애 시 친구의 게임 진행은 계속될 수 있어도
  서버 인증이 누락될 수 있다. 친구에게는 이벤트 등록과 서버 기록이
  정상인 것을 먼저 확인하고 진행하라고 안내한다.
- 엔딩을 봤는데 인증번호가 없으면 이벤트 화면의 **서버 기록 새로고침**
  및 (정상 엔딩 후만 노출되는) **인증번호 재요청**을 사용한다.
- 재요청도 실패한다면 관리자에게 해당 친구의 참가 ID/인증사진을 전달하도록 한다.
- 인증 서버에 장애가 생기면 상품 이벤트의 신규 접수를 중단하고 정상화 여부를 확인한다.

## 6. 의심 플레이 자동 관찰 · 상품 인증 보류 (이벤트 모드 전용)
- 브라우저에서 **실제 게임 중** 키/마우스/터치 행동의 **집계 수치만** 관찰한다.
  개별 입력 키 목록, 마우스 좌표, 화면, 개인정보는 서버에 전송하지 않는다.
  입력 통계는 약 45초마다, 일정 표본이 쌓였을 때만 전송한다.
- 관찰 신호: 사용자 입력이 아닌 합성 이벤트 반복, 물리적으로 극단적으로
  빠른 행동 버스트, 여러 번의 거의 오차 없는 기계적 반복.
  피격 횟수·회피 성공률·난이도·실력은 절대 의심 점수에 넣지 않는다.
- 서버는 점수의 출처가 브라우저라는 한계를 인정한 채 **지급 심사 신호로만 사용**한다.
  점수 **35점 이상** 관찰, **60점 이상** 추가 확인 권고,
  **85점 이상** `claim_hold=true`로 상품 인증 일시 보류.
  자동 계정 차단/보스전 종료/전투 입력 차단/상품 지급 거절은 없다.
- 참가자는 기존처럼 게임을 끝까지 플레이할 수 있다. 엔딩 완료 기록과
  인증번호도 생성할 수 있지만, `claim_hold=true`인 경우에는
  **상품 지급을 반드시 멈추고** 관리자 확인을 거쳐야 한다.
- 관리자는 Supabase Table Editor의 `public.oden_event_participants` 테이블에서
  `risk_score`, `risk_flags`, `risk_reports`, `last_telemetry_at`,
  `claim_hold`, `appeal_note`, `appeal_at`, `completed_at`, `paid_at`
  을 함께 검토한다. `risk_flags`는 의심 신호일 뿐 AI 사용 확정 증거가 아니다.
- 플레이어는 이벤트 화면에서 **최대 1회 소명(20~400자)**을 보낼 수 있다.
  관리자 확인 후 정당하면 `claim_hold=false`, `review_status=approved`
  로 변경한다. 실제 상품 지급 후에만 `paid_at`을 기록한다.
- 진짜 무단 코드 수정, 대리 플레이, AI 도구 사용은 이 통계만으로 100% 판별할
  수 없다. 보고를 전혀 전송하지 않는 조작 클라이언트도 존재할 수 있다.
  **보고 누락만으로는 자동 차단하지 않는다.**
- 일반 오든링은 영향을 받지 않도록 이벤트 모드 `enabled:false` 안전 잠금을 유지한다.
  전용 프로젝트에 SQL 컬럼과 Edge Function `index.js`·`risk.js` 배포는 완료했다.
  정상·오탐·의심 입력 실제 기기 테스트 후에만 이벤트를 연다.

### 권장 심사 순서
1. `claim_code`와 참가자의 전달 계정 및 캡처를 대조한다.
2. `claim_hold`가 false면 기존 정상 확인·승인 절차를 진행한다.
3. true라면 `risk_flags`를 확인하고 필요 시 직접 플레이/영상/디스코드
   화면공유 등에서 **추가 확인**한다. 의심 점수만으로 유죄로 판정하지 않는다.
4. `appeal_note`가 있다면 접근성 입력 장치나 매크로 오탐 등을 고려한다.
5. 납득할 만한 설명이 있으면 보류를 해제한다. 증명이 불충분한 경우에도
   지급 거절 전에 명확한 판단 근거를 남긴다.

## 7. 기존 세이브 1회 초기화 (이벤트 시작 때만)
- `src/legacy-save-reset.mjs`는 기존 일반 세이브 3개만 지운다:
  `oibung.journey.v1`, `oibung.gyuwon.ending-watched`, `oibung.gyuwon.ensemble-photo`.
- 현재 `enabled:false`라 **초기화는 아직 실행되지 않는다**.
  준비가 끝나 `src/oden-event-config.mjs`의 `enabled:true`가 배포된 후,
  친구가 **최신 오든링 페이지에 접속하는 순간** 최초 1회만 제거한다.
- 저장 마커 `oibung.odenring.legacy-save-reset.2026-11-10`은 이후 새로 얻은
  보스 해금·대장간 강화·엔딩 사진을 다음 접속에서도 보존하기 위한 것이다.
- 웹사이트에서 다른 친구의 브라우저 데이터를 원격으로 즉시 삭제하는 것은
  불가능하다. 이벤트 시작 이전에 열어 둔 구버전 탭과 다른 도메인의 복제본도
  직접 삭제할 수 없다. 과거 저장 스크린샷 역시 삭제할 수 없다.
- 소리/그래픽 설정, 다른 게임 데이터, **Supabase 이벤트 참가·인증 기록**은
  초기화하지 않는다. 이미 발급된 인증번호는 반드시 **이벤트 ID와 완료 시각**을
  확인한 뒤 지급 여부를 결정한다.
- 반드시 '이전 세이브는 이벤트 시작 후 최초 접속 시 사라집니다'라고
  모든 참가자에게 사전 안내한다. 배포 전 운영자도 별도 브라우저에서 검증한다.
